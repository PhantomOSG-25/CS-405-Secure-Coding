“Don’t leave security to the end” means security should be built into the program from the start instead of trying to add it after everything else is finished. I look at it the same way I would look at building a wall, running wiring, or treating a pest problem. If I know there is a weak spot and ignore it until the end, I may have to tear things back apart or do the whole job over again. In software, developers can prevent threats by checking user input, limiting access, protecting sensitive data, testing the code, and looking for problems as they build. Finding those problems early can save time, reduce mistakes, and keep a small issue from turning into a much bigger one.

A good example I could use in my Project Two presentation is adding unit testing and static code analysis throughout the development process. This reminds me of troubleshooting equipment in the field. I would not wait until the entire job was finished to find out that a hose was leaking, a machine was not spraying correctly, or a connection was bad. I would test each part as I worked so I could catch the problem before moving on. Software should be handled the same way. Unit tests can check that each part of the code works correctly, while static analysis can help find unsafe code, bad pointers, and other problems before the program is released. Building these checks into the normal process makes security part of the job instead of something that gets added at the last minute.
